1. Solução, justificativa e objetivos

O projeto RuaViva oferece uma API REST em Java 21 e Spring Boot 3.5 com Oracle para conectar o registro do morador ao atendimento da subprefeitura. O recorte inicial é a Liberdade, especialmente a Rua Barão de Iguape.

Justificativa e objetivos

A ausência de acompanhamento claro e a repetição de pedidos dificultam a organização do atendimento. A solução reúne registro, apoio, prioridade explicável e histórico de visitas. Objetivos: localizar demandas, considerar o impacto sobre idosos/PcD, expor a fila e manter consistência ao agendar, cancelar e concluir serviços.

Arquitetura e regras

Controller → BO → DAO → Oracle. Controllers expõem HTTP; BOs validam negócio e transações; DAOs usam SQL via JdbcTemplate; models representam as nove tabelas e enums; DTOs expõem composição e régua. GlobalExceptionHandler padroniza falhas.

Prioridade: peso × 10 + 2 por apoio + 15 se houver ponto sensível a até 200 m + 10 por autor prioritário. A distância usa Haversine; o ponto mais próximo gera um único bônus. Cadastros relevantes e apoios recalculam a pontuação.

Agendar coloca a ocorrência EM_ANDAMENTO; concluir coloca RESOLVIDA e cancela outras visitas agendadas. Cancelar a última visita reabre a pendência. A API recusa apoio próprio/duplicado, edição de histórico, exclusão de ocorrência resolvida e exclusão de atendimento concluído. Datas usam America/Sao_Paulo.

Os perfis do site são demonstrativos: não há autenticação/autorização no servidor. O notebook e o planejador são componentes separados. O prazo por categoria não equivale ao corte estatístico de sete dias.

3. Protótipos de tela

As telas conectam o fluxo de morador às operações da API. A identidade segue web/DESIGN.md. As capturas abaixo devem mostrar o protótipo real e preservar a indicação de demonstração.

Entrada

UC01 · US01

A placa identifica o serviço e o território. Morador e gestor têm caminhos claros; o amarelo destaca a ação principal. O aviso de demonstração explica a escolha de perfil.

Mapa do bairro

UC02 · US02

A lista aparece primeiro no celular. Números ligam registros e marcadores; os filtros Não resolvidos, Resolvidos e Todos apoiam a busca. Endereço e status escritos atendem quem usa zoom ou tem baixa visão.

Registrar problema

UC03–UC07 · US03–US05 e US09

Três passos: categoria com exemplos; localização por endereço, GPS ou mapa; detalhes e revisão. O endereço em texto confirma o ponto. Um pendente da mesma categoria a até 60 m oferece a alternativa de apoio. A descrição é opcional na tela; vazia, a API recebe o nome da categoria.

Detalhe do problema

UC07–UC09 e UC11 · US06–US07 e US09–US10

Endereço e situação aparecem antes do mapa. A linha do tempo apresenta datas disponíveis. “Isso também me afeta” explica o apoio; autor não apoia o próprio registro e casos encerrados não recebem novos apoios. A composição da prioridade é consultável na visão do gestor.

Fila do gestor

UC11–UC15 · US10–US13

A fila compara prioridade, endereço, apoios e prazo. O formulário abre na própria linha; oferece equipes ativas da mesma subprefeitura e datas a partir de hoje. Visitas ficam separadas e permitem concluir ou cancelar. Alta ≥ 60; média ≥ 40; baixa abaixo de 40.

4. Endpoints e respostas HTTP

Inventário dos dez controllers. Corpo de entrada em JSON; POST retorna 201 com Location; PUT retorna 200; DELETE retorna 204, sem corpo. Listas vazias retornam 200.

As colunas listam sucesso e erros de aplicação pertinentes. Comuns: 500 (inesperado); 503 em operações que acessam Oracle; 405 para método não permitido; 406 para Accept incompatível; 415 para Content-Type incompatível com corpo JSON. 400 cobre validação/JSON/parâmetros; 404, recurso ou referência inexistente; 409, integridade; 422, regra BO.

6. Execução, deploy e regressão

Ferramentas

IntelliJ IDEA, JDK 21, Maven 3.9 ou superior, Oracle FIAP e SQL Developer. Docker é usado para empacotar/executar o deploy. Para regressão: Bash, curl, jq e bc.

Passo a passo local

  1. Clonar o repositório e abrir java-api/pom.xml no IntelliJ IDEA; selecionar JDK 21 e importar o Maven.
  2. No Oracle FIAP, executar database/01_ddl.sql e database/02_dml.sql em UTF-8. Para recriar uma base de teste, conferir os nomes existentes antes de usar 00_drop.sql, que remove as tabelas e os dados.
  3. Configurar DB_URL, DB_USER e DB_PASSWORD no ambiente do terminal ou na configuração de execução do IntelliJ.
  4. Na pasta java-api, iniciar pelo Maven ou executar ZeladoriaApplication pela IDE.
  5. Abrir http://localhost:8080/ e a documentação em /swagger-ui.html. Exercitar cadastro, consulta, atualização e exclusão conforme as regras.
git clone https://github.com/0x4aron/RuaViva.git
cd RuaViva/java-api
export DB_URL="jdbc:oracle:thin:@oracle.fiap.com.br:1521:ORCL"
export DB_USER="seu_usuario_oracle"
export DB_PASSWORD="sua_senha_oracle"
mvn spring-boot:run

Deploy com Docker

Conectar o repositório a um Web Service no Render. Selecionar a branch main, diretório raiz java-api e runtime Docker, utilizando o Dockerfile existente. Cadastrar DB_URL, DB_USER e DB_PASSWORD no ambiente e executar o deploy. Conferir a raiz e /swagger-ui.html no endereço publicado.

# Na pasta java-api, alternativa para conferir a imagem localmente:
docker build -t ruaviva-api .
docker run --rm -p 8080:8080   -e DB_URL -e DB_USER -e DB_PASSWORD ruaviva-api

Link do deploy: LINK_DEPLOY

GitHub: https://github.com/0x4aron/RuaViva

Teste de regressão

Com a API ativa e uma base de teste recém-criada pelo DDL/DML, executar a partir da raiz do repositório:

bash java-api/testes/regressao.sh http://localhost:8080

O roteiro verifica ciclo de vida, equipe inativa, apoio, exclusões, integridade e concorrência. Ele cria e modifica dados; usar uma base destinada aos testes. Critério: todas as verificações aprovadas, sem linhas FALHA. Esta documentação não registra uma nova execução da regressão da API.
